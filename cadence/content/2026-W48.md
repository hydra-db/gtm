# LinkedIn drafts, 2026-W48

## 1. Proof point: what was true on Tuesday

**Hook:** What was true on Tuesday?

What was true on Tuesday?

That's the question most agent memory gets wrong. Not what was said, but what changed, and in what order.

Picture a user of a meeting note-taker app. They mention coming last in a swim meet. Weeks later: summer lessons, a 20% improvement, a trophy.

Now they ask "how's my swimming going?"

Vector or SQL search pulls every mention with no ordering. It might surface the stale "came last" result.

A graph follows the connected path in one retrieval: came last -> joined lessons -> improved 20% -> won a trophy. The full arc, not a fragment.

So we measured it. On BEAM 1M (a million tokens of history, questions about what changed and in what order), HydraDB scores 91 on temporal reasoning.

That's the number I care about most. Every company's data is a timeline. An agent that can't read the timeline answers with an old truth, confidently.

Pick one question where the answer changed twice, and ask your agent for the latest.

## 2. Objection: vector search is enough

**Hook:** Every agent demo works. Day 30 is where they break.

Every agent demo works. Day 30 is where they break.

The pushback I hear most: "we already have a vector database, our agent works fine."

It does. Few users, little context, similarity search finds the right chunk.

Then users add context. The user base grows. By day 30 the agent starts answering incorrectly, and nobody blames retrieval.

What actually broke, from teams we've talked to:

A deal went from $1K to $40K. Retrieval kept the old value.

A marketplace sent price updates for items that had already sold.

Neither is a similarity problem. Old and new text look alike. What the agent needed was which one is current, and what it's linked to.

Vector search answers "what looks like this?" Agents increasingly need "what is connected to this?" Until you have that, the linking lives in your glue code.

So keep your vector DB. Stop asking it to do a job it was never built for.

Pull the 3 to 5 queries your agent gets wrong today. For each one, ask: is this about what changed, or what's linked?

## 3. This week: graph on, graph off

**Hook:** A customer turned our knowledge graph on and off. The results were identical.

A customer turned our knowledge graph on and off. The results were identical.

They were right.

An AI startup ran a test on HydraDB last week. Graph context on, graph context off. Identical ranks.

My note to the team the next day: here is a real use case and we don't do this well.

Their question was a dependency question: which documents does this clause affect?

What our root cause found:

Similarity ranking picks documents that repeat the clause's wording, not the documents the clause actually governs.

In fast mode, the graph was read after ranking. It could only describe results search had already picked.

They added a custom extraction instruction. The graph changed. The search results didn't.

The lesson: adding a graph does nothing if it enters after the cut. Where the graph sits in the pipeline matters more than whether you have one.

What we're changing: find the clause's dependencies in the original files and use them before ranking. Not shipped yet.

If you've bolted a graph onto your retrieval stack, check one thing: does it enter before ranking, or after?
